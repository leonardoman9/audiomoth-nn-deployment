# Verification of the WrenNet port to AudioMoth (21 October 2026)

Goal: confirm as much as possible, without a board, of what was in doubt. For each item: what was done, the result, and
what remains open. Everything can be repeated with the scripts named. Nothing has been run on the chip.

## 1. Microphone configuration at 32 kHz
The official AudioMoth configuration app script (`constants.js`) uses, for 32 kHz: `sampleRate 384000`,
`sampleRateDivider 12`, `clockDivider 4`, `acquisitionCycles 16`, `oversampleRate 1`; default gain medium.
**Matches** `main_app.c`. The ADC is 12-bit differential with a 2.5 V reference (±1.25 V, LSB 0.61 mV).

## 2. Watchdog
`WDOG` period 64k on the 1 kHz ULFRCO = ~65 s (`audiomoth.c`, reference manual). The longest block (the network) takes a few
seconds: **no risk**; the watchdog is fed in the loops anyway.

## 3. External SRAM: 8-bit bus with wait states (a finding that changed the design)
`enableEBI()`: D8A8 mode, read 2+3+1 cycles, write 6 cycles **per byte**: a 32-bit access costs ~25 cycles (vs 1 for
internal RAM). `enableExternalSRAM()` and `enableFileSystem()` return false on `AM_VERSION_4` hardware (USB Microphone: no
SD and no SRAM); the Dev board, which has both, must detect as < 4 (cannot be checked without a board).

Profile with a QEMU plugin (`tools/memcount.c`, counts instructions and bytes per memory region), one 3 s window:

| stage | first design | after the redesign |
|---|---|---|
| front-end (301 frames) | 68 M instructions, **86 MB** to external SRAM (~13 s: overrun, every window dropped) | 44.8 M instructions, 0.85 MB (~1.3–1.8 s, 45–60 % CPU while recording) |
| backbone (4-D model) | 105 M instr., 16.3 MB (activations: ~67 KB in the arena) | unchanged: ~4.9–6.2 s |
| C tail | 55 M instr., no external accesses | unchanged: ~1.4–2.1 s |

Front-end redesign: constant tables in flash (generated by `tools/gen_frontend_tables.c`), working buffers in internal RAM
(6 KB), 1024-point real FFT computed as a 512-point complex FFT plus a split step; only the sample ring and the dB
spectrogram stay in external SRAM (sequential accesses). Verified result: ≤ 1 int8 LSB vs PyTorch.
Estimate per window (CPI 1.2–1.8 on the instruction count, plus EBI delays): backbone + tail take 6–8 s after the 3 s
recording, i.e. ~27–31 windows in 5 minutes; energy ~0.8–1.0 J per window at 21 mA / 4.1 V (not 0.077 J as in the paper).
These are estimates, not measurements.

## 4. Stack and internal RAM
Maximum stack measured in QEMU over the whole pipeline: **2,708 B** (2.7 KB); pipeline statics 7,024 B. Full application:
`.data` 192 + `.bss` 16,160 B (+ 3 KB reserved heap; 14,112 B before the recorder of section 13). Wide margin on 32 KB.

## 5. Flash
Complete firmware (application + classifier): **233,476 B of 245,760** (12.0 KB margin; 230,124 B before the hardening of section 12 and the recorder of section 13). TFLM+CMSIS-NN 53.6 KB (size build,
no-int4 patch in `firmware/patches/`), model 94.7 KB, tail 27.5 KB, front-end tables ~10 KB. The original AudioMoth linker
script compares a LENGTH with an ADDRESS (`__etext`), which makes it 16 KB stricter than the physical limit; fixed in our copy
(`firmware/audiomoth_tflm.ld`). The rest of the firmware (FatFS, audiomoth.c, emlib, filters) is ~36 KB (diagnostic build
without the network). The complete original AudioMoth firmware was ~150 KB: FatFS with code page 932 (60 KB) and libc/printf
(33 KB); here FatFS is trimmed (CP437, 8.3 names, **no exFAT: FAT32 card**).

## 6. FatFS + AudioMoth file-system wrappers (test on a FAT32 image)
`tests/fstest/` (`run_fstest.sh`): the real FatFS with the trimmed configuration, plus the file functions of `audiomoth.c`
copied verbatim, on a 128 MB FAT32 image. **PASS**: CONFIG.TXT read and marked, 120 lines appended (open/write/close), files
read back correctly by an independent FAT reader (mtools). One defect found and fixed: `f_rename` fails if the target exists
(the simulator hid this); CONFIG.TXT is now overwritten with "APPLIED <time>". The SPI driver (`microsd.c`, vendor code,
unmodified) has not been executed: still to be tested on the board.

## 7. Clock and sleep
EM4 (RAM lost, BURTC kept): every wake-up is a reboot, as intended. Long sleeps use `powerDownAndWake(s, true)` (the
unsynchronised version would multiply ms*1024 and overflow beyond ~70 min), in 6 h chunks. The time is lost if power is lost
(datasheet): a new CONFIG.TXT is needed. Drift ±0.89 s/day.

## 8. Class order (error found, now confirmed on all species)
The real order is that of `allowed_bird_classes` (0 Bubo bubo, 1 Certhia familiaris, 2 Apus apus, 3 Certhia brachydactyla,
4 Emberiza cia, 5 Lophophanes cristatus, 6 Periparus ater, 7 Poecile montanus, 8 non-bird), not the one in the training log.
Direct test with real recordings from the project Drive (3 s windows, most-voted index per true species): Bubo 19/23 -> 0,
Certhia fam. 13/14 -> 1, Apus 20/23 -> 2, Certhia brach. 12/14 -> 3, Emberiza 13/23 -> 4, Lophophanes 10/14 -> 5,
Periparus 19/24 -> 6, Poecile 17/24 -> 7: **8 species out of 8**, 76 % of windows correct. Fixed in `schedule.c` and in the tools.

## 9. Accuracy on the real species (data from the project Drive)
161 windows of 3 s (the 2 loudest per file, 7–12 files per species), all 8 species.

| | accuracy |
|---|---|
| PyTorch float, clean audio | 76.4 % |
| device pipeline (C front-end + int8 backbone + C tail), clean audio | 75.8 % |
| PyTorch float, simulated analogue chain at 70 / 60 / 50 dB SPL | 73.3 % / 73.9 % / 73.3 % |
| device pipeline, simulated chain at 70 / 60 / 50 dB SPL | 75.8 % / 75.8 % / 75.2 % |

Per class (float, clean): Bubo 0.79; Certhia fam. 0.93; Apus 0.87; Certhia brach. 0.86; Emberiza 0.54; Lophophanes 0.71;
Periparus 0.79; Poecile 0.71. Reading: int8 + C cost < 1 point; the simulated analogue chain costs ~2–3 points on the float
model and almost nothing on the int8 pipeline.
**Limits:** small sample (±3–4 points), windows picked by energy rather than with the training's call extraction, no non-bird
windows, and the Drive files are probably also training files (absolute accuracy is optimistic; the relative comparison is
what counts). Scripts: `tools/bird_eval_prepare.py` + `tools/bird_eval_pipeline.py`; Xeno-canto download: `tools/xc_fetch.py`
(API key). These are in the WrenNet repository.

## 10. On-device test modes
`REPLAY.PCM` ("RPLY" + 96,000 int16 samples + "END!") on the SD card: the device classifies it and writes
`REPLAY,<log line with the 9 logits>`; tested in the simulator (difference 0.044 from PyTorch). Diagnostic build
`EXTRA_CF=-DBIRD_DIAG_RECORD firmware/app/build_app.sh ...`: records 3 WAV files (`HHMMSS.WAV`) without the network, 36 KB of
flash; tested in the simulator (5 % error above 300 Hz vs the 12-bit-quantised source).

## 11. Compiler: GNU Arm 10.3-2021.10 (the one the AudioMoth Makefile expects) vs 14.3.1
TFLM (same commit + patch) and the firmware rebuilt entirely with 10.3.1 20210824. **PASS**: 0 warnings in the library and
in the firmware (apart from the usual newlib `_read`/`_lseek` stubs), identical QEMU PCM->logits pipeline (max|d| vs host
0/1000, same argmax), stack 2,712 B.
Flash with the same TFLM flags:

| TFLM flags | GCC 14.3.1 | GCC 10.3.1 |
|---|---|---|
| `BUILD_TYPE=release` (kernels at -O2) | 244,620 B | 239,608 B |
| + `KERNEL_OPTIMIZATION_LEVEL=-Os THIRD_PARTY_KERNEL_OPTIMIZATION_LEVEL=-Os OPTIMIZE_KERNELS_FOR=KERNELS_OPTIMIZED_FOR_SIZE` | **230,124 B** | **230,024 B** |

The size flags are required (without them the margin drops below 1.2 KB with 14.3); with them the two compilers are
equivalent (-100 B). An earlier version of this section compared 10.3 without the flags against 14.3 with them, and was wrong.

## 12. Robustness: sanitizers, static analysis, fault injection, long run
- **Sanitizers.** The simulator built with AddressSanitizer + UBSan (`SAN=1 tests/sim/build_sim.sh`), the schedule tests and
  the FatFS test. ASan found a stack overflow, in the FatFS test's 64-byte line buffer. Checking the firmware side showed
  that the device's 128-byte buffer held every normal line (~100 B), but a NaN, infinite or huge logit made the
  `(int32_t)` cast undefined and could make a line ~165 B long. **Fixed:** logged values are clamped to ±999999 (NaN → 0)
  and the percentage to 0–100, with tests for these cases. After the fix: 2 simulated days, all fault scenarios and the
  schedule/FatFS tests run clean under the sanitizers, and the log is identical to the normal build.
- **Static analysis.** clang static analyzer and `-Wall -Wextra -Wshadow -Wconversion` on `main_app.c`, `schedule.c`,
  `bird_frontend.c`, `bird_tail.c`: no findings (the analyzer was checked on a file with a planted bug). ARM GCC with
  `-Wall -Wextra` on the device build: no warnings in our code; the vendor `audiomoth.c` has harmless ones (unused
  parameters, an unsigned value clamped against 0, an enum whose values match emlib's HFRCO bands). Vendor code untouched.
- **Fault injection** (`SIM_FAULT` in `hal_sim.c`, 21 scenarios in `tests/sim/run_faults.py`, all PASS): no SD card at first
  boot (retries every 60 s); SD or external SRAM lost after the clock is set (no session, sleeps to the next window, no
  tight loop); every SD write failing, or LOG.TXT not opening (red blinks, session runs to its end); classification
  failing; watchdog-style reset mid-session (logging resumes in the same window); power cut mid-session (lines written
  before the cut survive intact; the clock is lost and the device waits for a new CONFIG.TXT, which then works); six
  malformed CONFIG.TXT files and a missing one; three malformed REPLAY.PCM files (rejected, truncated, the normal session
  still runs); a silent microphone (zero spread in the per-clip normalisation: lines stay finite and well formed).
  **Found and fixed:** CONFIG.TXT `2026-02-30 07:00:00` was accepted (impossible dates are now rejected), and
  `06:58:309` was read as 06:58:30 (only whitespace may follow the time now).
- **Long run.** 400 simulated days from 2027-12-30 (two new years, the leap day 2028-02-29) with the real network
  (`run_scenario.py` + `tests/sim/check_long_run.py`): **PASS**, 1,798 boots, 19,400 lines, every day present once and
  in order, 48 or 49 lines per day, all inside 07:00–07:05, no broken values, no red LED. LOG.TXT grows by ~3.5 KB per
  day (1.41 MB after 400 days; FAT32 allows 4 GB).

## 13. Record the whole window, then classify it
The window used to be classified while recording: 3 s heard, then 6–8 s of computation with the microphone data
dropped, so only ~30 % of the window was heard. Now the whole window is recorded to the card (`YYYYMMDD/HHMMSS.WAV`),
then read back and classified window by window (hop from the model package, 1–3 s). Progress is kept in `STATE.TXT`;
`SESSIONS.TXT` gets one summary line per session.

**How it works**
- **Recording.** The DMA handler writes into a 1.5 s ring (96 KB of external SRAM). The main loop copies 4 KB chunks
  to internal RAM and writes them to the card, syncing every 40 chunks (~2.6 s). The WAV header is padded to 512 B, so
  the writes are sector-aligned.
- **Card problems.** If the card falls more than the ring behind, or a write fails (busy > 500 ms, card full), the file
  is reopened, the lost stretch is written as silence and counted, and the timeline stays exact.
- **Timing.** The board wakes 2 s before the window and starts on a whole second, so the file name and every
  `LOG.TXT` time are the sample times.
- **Resume.** A reset or power cut is resumed at the next boot even without a clock, which any non-EM4 reset clears
  (audiomoth.c). `STATE.TXT` is a fixed 96 B record rewritten in place. A window started by 3 boots without finishing
  is skipped, and a pending session that cannot be classified at all for 3 boots is abandoned. No new session starts
  while one is pending.

**Review** (an independent agent read the code and ran its own experiments, including on the real FatFS). It found
problems the first version's tests did not:
1. **Resets lost the clock, so the resume never ran.** On the board, any reset other than an EM4 wake clears the
   clock (watchdog, brown-out, lockup, power cut). The resume sat behind the clock check, so it never ran. The
   simulator had kept the clock on `reset=`, hiding this.
2. **A cut while saving the state abandoned the session.** `STATE.TXT` was rewritten with `FA_CREATE_ALWAYS`, which
   truncates at once, so a cut between the open and the write left it empty. Shown in the simulator and on FatFS.
3. **A write failure overcounted the samples.** The header lied and the last window was classified partly from stale
   buffer data (short reads return FR_OK).
4. **A single long stall aborted the recording.** The SD driver fails any write that waits over 500 ms, and the file
   object stays in error; the simulator had modelled a long stall as a slow write that succeeds.
5. **Gaps were overcounted.** The silence skip threw away ~0.3 s of intact audio at each overflow.
6. **Times were up to ~2 s early**, and hops under 1 s repeated timestamps.
7. **Configuration limits were missing.** Very long windows overflowed 32-bit sizes, and classification could
   overlap the next window.

All fixed. **A second review of the fixes** found three more problems, also fixed:
1. `scripts/run_tests.sh` used `cmd | tail` under plain `sh` (no pipefail), so CI could have passed with failing
   fault scenarios.
2. A crashing window was attempted 4 times instead of 3.
3. A pending recording that could never be opened blocked every new session for weeks.

It also found that a start delayed by a slow card left the planned time in the file name. Now the missed seconds are
written as silence, so names and times stay exact. The classification margin in `gen_model_config` is 12 s per
window.

The simulator now behaves like the library and FatFS:
- **Resets** lose the clock.
- **Failed writes** leave half their bytes on the card, and the error sticks until the file is reopened.
- **Stalls** longer than 500 ms fail.
- **New faults:** `wfail` makes one write fail; `diskfull` fills the card.
- **Opening a second file** stops the run.
- **Opening a folder as a file** fails.
- **File opens** can be made slow (`SIM_SD_OPEN_MS`).

**Results** (simulator with ASan+UBSan unless stated)
- **Content.** The 300 s recording equals the microphone input over its whole length (relative error 0.026 above
  300 Hz, the 12-bit quantisation alone; `tests/sim/check_recording.py`). Every classified window is exactly the
  matching slice of the WAV. Device vs PyTorch on those windows: 95/100 same class; the 5 differences all have
  PyTorch confidence ≤ 0.33.
- **FatFS** (`tests/fstest/`, ASan/UBSan). It runs the same sequence:
  - a folder, then 300 s in 4 KB writes with syncs;
  - the header rewrite, `getFileSize`, and read-back by seek with every sample checked;
  - the state rewritten in place: a cut during that rewrite (open + seek + partial write, unmount without close)
    keeps the old record;
  - a read past the end of a file returns FR_OK with nothing read.

  mtools reads a valid 19,200,512-byte WAV.
- **Fault injection: 44 scenarios, all PASS** (`tests/sim/run_faults.py`). Among them:
  - **SD busy:** 400 ms loses nothing; 3 s loses 0.03 s (the write fails after 500 ms, the ring covers the rest).
  - **One write failing mid-recording:** same recovery.
  - **Full card:** recording stops at the limit with a correct header; only windows in the file are classified, none
    from stale data.
  - **Slow cards:** 50 ms per write loses nothing; 80 ms (slower than real time) keeps the file length.
  - **Reset and power cut:** during the recording, the next boot classifies the synced part without a clock. During
    the classification, it resumes.
  - **Power cuts at 25 times** across the recording and classification, including inside the state saves: every
    window logged once, at most one repeated.
  - **Bad state:** corrupt, empty, out-of-range or orphaned `STATE.TXT`.
  - **A window that crashes the board:** after 2 crashes the 3rd try logs it; after 3 crashes it is skipped.
  - **An unreadable pending recording** (`CLS` or `REC`): abandoned at the 3rd boot, then the session runs.
  - **A slow card delaying the start by 2 s:** the missed seconds become silence, and the times stay exact.
  - **Little time left:** boots with 5, 4 and 3 s left.
  - **Replay then session** in the same boot.
  - **The earlier scenarios.**
- **Long run.** 62 simulated days from 2027-12-30 (new year, leap day): **PASS**, 100 windows every day, 62 complete
  sessions, 0 samples lost, ~19 MB per day (~3.5 GB in 6 months). This was before the review fixes; the 2-day runs
  and the fault scenarios cover the fixed version.
- **Other packages:** every test also passes with 3 classes (13:30, 10 min), 40 classes (23:50, 8 min, so the
  classification runs past midnight) and a 1.5 s hop (199 windows per session), in CI as well.
- **Earlier bugs found while doing this:**
  1. `NNBird_Init` failed the second time in one boot (TFLM refuses to register an operator twice), so a replay
     followed by a session lost the session.
  2. A processed `REPLAY.PCM` (1 byte) made the board blink 6 times at every boot.
  3. In the simulator: `readFile` failed on short reads, which FatFS does not do, and wake-ups ignored the
     whole-second alignment of `powerDownAndWake(s, true)`.
- **Cost.** Flash 233,476 B (+3.1 KB); external SRAM 258,512 of 262,144 B; internal `.bss` 16,160 B. Time awake per day:
  5 min of recording + the classification (estimate 6–8 s × 100 windows ≈ 10–13 min).
- **Still to measure on the board:**
  - the card's write speed and stalls while recording;
  - the energy of the longer time awake;
  - whether keeping the clock across a watchdog reset is possible by changing the library (today any such reset
    stops the sessions until a new `CONFIG.TXT`).

## 14. Still open (needs the board or more data)
Boot and external SRAM enable on the chip; real DMA/ADC capture and levels; the real SD driver; real timing and power (the
estimates above can be off by ~2×); true accuracy on the test set (the Drive dataset lacks the training's test split, and
the `os.listdir` order is not reproducible); domain gap with real device audio.
